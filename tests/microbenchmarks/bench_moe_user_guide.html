TensorRT-LLM MoE Microbenchmark

bench_moe.py 用户使用指导

tests/microbenchmarks/bench_moe.py 是一个面向 MoE layer 的微基准工具， 它直接计时 ConfigurableMoE.forward，用于比较 MoE backend、通信方式、EPLB、 并行模式、CUDA Graph、combine 精度，以及 高级 routing 控制（可控的 source→target dispatch traffic 与 expert histogram）。

本指南基于当前脚本实现重新生成，包含运行方法、参数语义、JSON 输出、典型应用案例和 已知限制；routing-control 相关参数全部映射到 BENCH_MOE_ROUTING_CONTROL_DESIGN.md。

1. 这个工具测什么

测量对象

计时对象是 ConfigurableMoE.forward，包含 routing、dispatch、MoE backend 计算、 activation、combine 等 MoE 模块内部阶段。它不是 full decoder layer benchmark。

输入方式

使用 synthetic hidden states 和 router logits，不依赖 HuggingFace checkpoint。 Token 数由 num_tokens + 可选的 per_rank_num_tokens 决定； 路由形状可以由模型原生 logits 决定，也可以通过 routing-control 显式约束。

主要用途

生成 dashboard 可消费的 structured JSON，并回答：给定 model shape、token 数、 以及可控的 routing 流量分布时，哪个 backend / comm / EPLB / parallel mode 最快。

推荐理解方式： 先选择 model，再 sweep num_tokens，然后用 routing control 决定要研究什么 routing 形状，最后搜索 runtime configuration。

2. 快速开始

单卡固定 backend，关闭 CUDA Graph

python tests/microbenchmarks/bench_moe.py \
  --world_size 1 \
  --model qwen1.5_moe \
  --backend CUTLASS \
  --num_tokens 16 64 \
  --no_cuda_graph

  --search backend \

  --num_tokens 64 256 \

  --config_file configs/moe_dashboard_deepseek_v3.json

场景 命令形式 说明

Import 行为： 脚本会把 tests/unittest 加入 sys.path，以便直接复用 MoE unittest helper。 对 tensorrt_llm 主包，只有当当前源码树里存在已编译的 tensorrt_llm/bindings 时才优先使用源码树；否则会使用环境里已经安装好的 TensorRT-LLM wheel。这适合 OCI / 预构建容器里"源码 checkout + 已安装 wheel"的运行方式。

5. Workload：token 数和路由分布

参数 默认值 说明
--num_tokens 必填 要 sweep 的全局 token 数列表。每个值都会按 rank split 规则切分到各 rank。
--rank_imbalance_ratio 0.0 Legacy rank 间 token 不均衡比例，范围 [0, 1]。 0 均匀切分，1 全部放到 rank0。 只控制 source-rank 本地 token 数 / max_num_tokens_per_rank； 不控制 dispatch traffic matrix。新用法推荐 --per_rank_num_tokens。
--per_rank_num_tokens None 显式 per-rank token 列表（逗号分隔，长度必须等于 world_size， 总和必须等于 --num_tokens）。优先级高于 rank_imbalance_ratio。
--expert_distribution balanced_patch Legacy synthetic routing 方式。可选 balanced_patch 或 hotspot。 hotspot 会被自动映射到 --expert_pattern hotspot,hotness=…。
--expert_hotspot_ratio 0.0 Legacy 专家热点比例，范围 [0, 1]。 若 --expert_pattern 还是默认 balanced， 会被自动转成 expert_pattern=hotspot,hotness=<ratio>。
--force_balance_patch false Legacy 在 expert_hotspot_ratio=0 时也强制走 balanced patch。 等价于 --routing_mode forced --comm_pattern balanced_alltoall --expert_pattern balanced， 并按设计文档自动迁移。

6. 高级 routing control

Routing control 让 benchmark 能 显式控制 dispatch / all-to-all 通信流量形状和 expert 热点， 用于复现可控的 routing workload。它和模型原生 routing 兼容：你可以让模型继续走原生 fused routing （native 模式），也可以直接 supply top-k ids/scales（forced 模式）。 完整设计见 BENCH_MOE_ROUTING_CONTROL_DESIGN.md。

核心参数

参数 默认值 说明
--routing_mode native native：保留模型原生 logits / fused routing，benchmark 反推 logits 把 top-k 推向计划的形状。
forced：直接 materialize topk_ids + 均匀 1/top_k scales， 绕过 fused scoring，但保留后续 metadata / permutation / grouped GEMM。
--projection_policy project 仅作用于 native 模式：
project：当原生 logits 无法精确表达时，使用最接近的合法 projection 继续运行， 并在结果里记录 routing_realization.status="projected" 与偏差。
reject：直接跳过该 case 并写入 skip_reason。
--comm_pattern balanced_alltoall source → target slot dispatch 形状。见下表。
--expert_pattern balanced 每个 target rank 内部的 local expert 直方图形状。见下表。
--routing_scenario None 预设组合，等价于 routing_mode / projection_policy / comm_pattern / expert_pattern 的特定取值（见下表）。显式参数总是优先于 scenario。
--routing_dump_matrix false 在每行结果中输出完整 observed_slot_dispatch_matrix / observed_token_dispatch_matrix / observed_expert_histogram。 默认只输出 summary，避免大 sweep JSON 膨胀。
--routing_seed 0 routing-plan materialize 时的确定性 seed。同 seed 输出一致。

Comm patterns

名称 语义 典型例
balanced_alltoall 每个 source rank 把 selected slots 尽量均匀发送到所有 target ranks。公平基线。 --comm_pattern balanced_alltoall
receiver_hotspot 每个 source row 把 hotness 比例的 slots 转向 rank=<k>。 研究接收端带宽 / 排队瓶颈。 --comm_pattern receiver_hotspot,hotness=0.75,rank=0
pair_hotspot 只让 src=<s> 行把 hotness 比例的 slots 转向 dst=<d>。研究单条 peer-link 热点。 --comm_pattern pair_hotspot,hotness=0.5,src=0,dst=1
local_only 所有 slot 都留在本 rank。研究最低通信量 baseline； 原生路由通常不能精确表达，需要 --projection_policy project 或显式 --routing_mode forced。 --comm_pattern local_only
ring source i 全部发往 (i+1) % ep_size。结构化 peer traffic。 --comm_pattern ring
file:<path> 从 JSON 加载 slot dispatch matrix（schema=v1， 字段 slot_dispatch_matrix 是 ep_size × ep_size 整数矩阵）。 每行 row sum 必须等于 per_rank_num_tokens[src] × top_k。 --comm_pattern file:matrix.json 
// matrix.json
{
  "schema": "v1",
  "ep_size": 4,
  "slot_dispatch_matrix": [
    [64, 64, 64, 64],
    [64, 64, 64, 64],
    [64, 64, 64, 64],
    [64, 64, 64, 64]
  ]
}

Expert patterns

名称 语义 典型例
balanced 每个 target rank 内 slots 在 local experts 间近似均匀。 --expert_pattern balanced
hotspot,hotness=… 每个 target rank 把 hotness 比例的 slots 集中到 1 个 local expert。 --expert_pattern hotspot,hotness=0.5
hotspot,active_experts=… 每个 target rank 内只有 active_experts 个 expert 承担全部 slots。 --expert_pattern hotspot,active_experts=2
file:<path> 从 JSON 加载 expert histogram（schema=v1， 字段 expert_histogram 是 ep_size × experts_per_rank 整数矩阵）。 全局总和必须等于 sum(per_rank_num_tokens) × top_k。 --expert_pattern file:hist.json

Routing scenarios（preset 组合）

scenario 等价展开
balanced_baseline native + project + balanced_alltoall + balanced
receiver_hotspot_75 native + project + receiver_hotspot,hotness=0.75,rank=0 + balanced
pair_hotspot_50 native + project + pair_hotspot,hotness=0.5,src=0,dst=1 + balanced
local_only_baseline native + reject + local_only + balanced（不可精确表达就跳过）

各 routing method 的反推能力

Routing method capability 说明
Defaultexact_ids目标 expert ids 精确；scales 来自 softmax，不可任意指定。
Renormalize / RenormalizeNaiveexactids + scales 都可精确控制。
SigmoidRenormexact_idsids 精确；scales 受 sigmoid 限制。
Llama4top1_exact只能表达 top1；top_k > 1 时退化为 projected。
MiniMax2exact_with_zero_bias当 score-correction bias 为 0 时 ids 精确。
DeepSeekV3projected_or_exact受 n_group/topk_group 约束，可能 projected。
SparseMixerunsupportedv1 不支持精确反推，统一标 projected。

enable_perfect_router 选择规则

routing_mode comm_pattern expert_pattern perfect_router
nativebalanced_alltoallbalancedon
native其它任何任意off（避免和 projection 冲突）
forced任意任意off
EPLB 互斥： v1 中 routing control 与 eplb_mode != off 互斥，会被直接 reject， skip_reason 写明原因。EPLB 的 slot remapping 需要在后续版本里独立支持。

7. Runtime 配置

Backend

--backend 默认是 TRTLLM。也可以传具体 backend，或在搜索模式下使用 ALL。脚本会先调用 backend can_implement() 做 capability gate， 不支持的候选会以 status="skipped" 写入结果。

并行模式

模式 moe_ep_size moe_tp_size enable_attention_dp 典型含义
DEPworld_size1trueData Parallel attention + Expert Parallel MoE。
TEPworld_size1falseTensor Parallel attention + Expert Parallel MoE。
DTP1world_sizetrueData Parallel attention + MoE TP。
TTP1world_sizefalseTensor Parallel attention + MoE TP。
CUSTOM用户指定用户指定用户指定高级自定义布局。
 
python tests/microbenchmarks/bench_moe.py \
  --world_size 4 \
  --model deepseek_v3 \
  --parallel_mode CUSTOM \
  --moe_ep_size 2 \
  --moe_tp_size 2 \
  --enable_attention_dp \
  --backend TRTLLM \
  --num_tokens 256

通信方式

--comm_method 支持 AUTO、NVLINK_ONE_SIDED、 NVLINK_TWO_SIDED、DEEPEP、DEEPEPLOWLATENCY、 ALLGATHER。当前实现仍通过 TRTLLM_FORCE_COMM_METHOD 在单个 case 内注入强制通信方式，并在 case 结束后恢复环境变量。

限制： --per_case_subprocess 当前只是 no-op stub，会打印 warning 后回退到 in-process。 大规模 dashboard sweep 仍需注意同一进程内多 case 的状态共享。

EPLB

参数 说明
--eplb_mode off不启用 load balancer。
--eplb_mode static启用 slots 和 routing bookkeeping，但 timed iterations 中不迁移权重。
--eplb_mode dynamic允许运行时统计和权重迁移；必须配合 --no_cuda_graph。
--num_slots覆盖 slot 数。未指定时脚本会从模型和 EP size 推导。
--layer_updates_per_iter覆盖动态 EPLB 每轮更新层数。

8. 搜索模式

--search 搜索维度
none只运行当前配置。
backend搜索 backend。配合 --backend ALL 最常用。
comm固定 backend，搜索通信方式。
parallel搜索 DEP / TEP / DTP / TTP。
eplb搜索 off / static / dynamic。
full搜索 backend、parallel、comm、EPLB、CUDA Graph 开关。

搜索候选会先展开笛卡尔积，再通过 backend capability、mapping、EPLB/CUDA Graph 兼容性、 forced comm 合法性剪枝。被剪枝的候选不会丢失，会作为 status="skipped" 结果行输出。

限制搜索规模

python tests/microbenchmarks/bench_moe.py \

  --model deepseek_v3 \
  --search full \
  --backend ALL \
  --num_tokens 64 128 256 \
  --max_configs 20 \
  --time_budget_minutes 30 \
  --output_file out/moe_full_limited.json

9. Timing 与 analysis

参数 默认值 说明
--no_cuda_graph默认不开启该 flag默认使用 CUDA Graph timing；传该 flag 改成 eager timing。
--warmup1timed loop 前的 warmup 次数。
--iters5计时迭代次数。
--fast_autotunefalse缩短 autotune repeat/warmup，适合快速调试。
--analysiskernels可传 summary、phases、kernels、phases,kernels。
--dtypebfloat16activation dtype，可选 bfloat16 或 float16。
当前 phase 状态： --analysis phases 的 CLI 已存在，但 scheduler-side phase marker 尚未实现。 当前输出中 phase_timing_available=false，phase_times_us 为空结构。

Autotune 是 untimed pre-pass：脚本会在正式 timing 前运行一次 autotune(...)， 用来填充 kernel cache。正式 latency 不包含这个 autotune pass。

10. 输出 JSON 解读

rank0 会在 stdout 打印 header 和每个 result row。如果传了 --output_file， 最终完整 payload 会写入文件。 

{
  "schema_version": 3,
  "benchmark": "bench_moe",
  "environment": { "...": "..." },
  "model": { "...": "..." },
  "search": { "...": "..." },
  "base_config": { "...": "..." },
  "results": [],
  "rankings": []
}

单个 result row 的关键字段

字段 含义
workload本 case 的 token 设置、per-rank token 列表，以及 routing_control 请求 spec。
requested_config用户请求或搜索生成的配置。
actual_config实际运行到的 backend、comm、scheduler、EP/TP、chunk 数。
statussuccess、skipped 或 failed。
latency_us.score默认 score 为每次迭代取最慢 rank，再对迭代求平均。
kernel_breakdownkernel 分类统计，包含 moe_forward_kernels 和 other_kernels。
routing_control请求与实际 routing 形状的对比（见下）。开启 routing-control 时存在。
rankings按 (num_tokens, parallel_mode) 分组，对所有结果按 score 排序。

12. 常见问题和限制

现象 原因 / 处理方式
Custom shapes ... AUTO has no safe default 自定义 shape 必须显式指定 --routing_method。
动态 EPLB 被 skip eplb_mode=dynamic 与 CUDA Graph 不兼容，请加 --no_cuda_graph。
routing-control 与 EPLB 同时开 v1 直接 reject，skip_reason 会写明原因；二选一。
forced comm 被 skip 非 DP、MoE TP、或 world_size=1 时部分通信方式没有意义，会被候选剪枝拒绝。
routing_realization.status="projected" routing method 不能精确反推请求的形状（最常见：DeepSeek-V3 grouped routing， Llama4 top1-only）。检查 max_abs_slot_error 判断偏差是否可接受。
routing_realization.status="rejected" 用户传了 --projection_policy reject 而又请求了不可精确表达的 pattern。 该 case 会作为 skipped 行输出，仍保留 routing_control summary。
forced 模式在 TEP 下结果不能和 native 比 forced 会 patch TRTLLMGenFusedMoE.run_moe，跳过 fused scoring； 它度量的是 supplied-topk 的执行路径，不是 native fused routing。
file: 形式的 dispatch matrix 报 row-sum 错 每行 row sum 必须等于 per_rank_num_tokens[src] × top_k； ep_size 必须和 runtime moe_ep_size 一致。
per_rank_num_tokens 报长度错 长度必须等于 world_size，总和等于 --num_tokens。
phase_times_us 为空 当前 scheduler-side phase marker 尚未实现；只能看 latency 和 kernel breakdown。
--per_case_subprocess 没有真正隔离 当前是 no-op stub，只打印 warning 后继续 in-process。
某 backend 出现在 skipped 行 backend can_implement()、mapping、EPLB 或 comm gate 不满足；看 skip_reason。
CUDA Graph timing 没有 kernel breakdown CUPTI 需要在 CUDA context 创建前初始化；失败时会标记 cupti_available=false 或跳过 breakdown。
