TensorRT-LLM MoE Microbenchmark

bench_moe.py 用户使用指导

tests/microbenchmarks/bench_moe.py 用 synthetic inputs 直接计时 ConfigurableMoE.forward，最常见的用途是：给定模型 shape、token 数和 routing 形状后， 比较不同 backend、communication method、并行布局、 routing 形状和 CUDA Graph 设置的 MoE latency。

推荐阅读顺序：先看 三步用法 和 常用案例，再看 搜索空间， 最后查 重点选项含义。

1. 先掌握三步用法

第一步：定 workload

选择 --model 或显式 shape，再用 --balanced_total_num_tokens 指定要测的 token 数。 多卡场景默认把 token 尽量均分到各 rank；需要 source-rank skew 时再加 --per_rank_num_tokens。

第二步：定要搜什么

最常用的是 --search backend 搜所有 backend，或 --search comm 固定 backend 搜通信方式。--backend、--comm_method、 --parallel_mode 都支持多值，例如 --backend CUTLASS DEEPGEMM 只搜这两个；传 >1 个值会自动开启对应搜索轴。--max_configs 控制规模。

第三步：看 winner 和 skip reason

结果 JSON 里 rankings 会按 (num_tokens, parallel_mode) 分组给出 winner。 不支持的 backend、comm 或 parallel 组合不会静默消失，而是以 status="skipped" 和 skip_reason 出现在结果里。

一句话模板： python tests/microbenchmarks/bench_moe.py --world_size N --model MODEL --parallel_mode DEP --balanced_total_num_tokens ... --search ... --output_file out.json

2. 常用案例

下面这些命令覆盖了最常见的用途。刚开始用时可以直接复制一个案例，再改 --model、--balanced_total_num_tokens 和搜索空间。

案例 A：单卡 sanity，确认环境能跑

python tests/microbenchmarks/bench_moe.py \
  --world_size 1 \
  --model mixtral_8x7b \
  --backend CUTLASS \
  --balanced_total_num_tokens 8 \
  --no_cuda_graph \
  --analysis none

用途：确认 import、CUDA、backend 构建和 basic timing 能跑通。

案例 B：4 卡 DEP，搜索所有 backend

python tests/microbenchmarks/bench_moe.py \
  --world_size 4 \
  --parallel_mode DEP \
  --model deepseek_v3 \
  --search backend \
  --balanced_total_num_tokens 64 128 256 512 \
  --output_file out/deepseek_v3_backend_search.json

用途：回答“在每个 token count 下，哪个 backend 最快”。 单写 --search backend 默认展开为全部 backend；等价写法 --backend ALL。 要只比较其中两个，可写 --backend CUTLASS DEEPGEMM（多值会自动开启 --search backend，可不必显式声明）。

案例 C：固定 backend，搜索通信方式

python tests/microbenchmarks/bench_moe.py \
  --world_size 4 \
  --model deepseek_v3 \
  --parallel_mode DEP \
  --backend TRTLLM \
  --search comm \
  --balanced_total_num_tokens 256 \
  --output_file out/deepseek_v3_comm_search.json

用途：回答“TRTLLM backend 下 AUTO、NVLink、DeepEP、AllGather 哪个通信路径最好”。

案例 D：同时搜索 backend 和 comm

python tests/microbenchmarks/bench_moe.py \
  --world_size 4 \
  --model deepseek_v3 \
  --parallel_mode DEP \
  --search backend comm \
  --balanced_total_num_tokens 64 128 256 \
  --max_configs 40 \
  --output_file out/deepseek_v3_backend_comm_full.json

用途：让搜索空间覆盖 backend 和 comm，其它轴用 base config。 省略 --backend 和 --comm_method 时，两个轴都默认展开为全集。 要只比较子集，例如 --backend CUTLASS DEEPGEMM --comm_method NVLINK_ONE_SIDED DEEPEP （多值会自动开启对应搜索轴，可省略 --search；也可显式写以表意更清晰）。 多个搜索轴用空格分隔；逗号写法 --search backend,comm 也能解析，但推荐空格写法以对齐 --balanced_total_num_tokens 64 128 256 这类多值选项。

案例 E：receiver-hotspot，研究接收端通信压力

python tests/microbenchmarks/bench_moe.py \
  --world_size 4 \
  --parallel_mode DEP \
  --model deepseek_v3 \
  --backend TRTLLM \
  --balanced_total_num_tokens 256 \
  --comm_pattern receiver_hotspot,hotness=0.75,rank=0 \
  --output_file out/recv_hotspot.json

用途：把 75% 的 selected slots 打到 rank0，观察 receiver hotspot 对通信和整体 latency 的影响。

案例 F：source-rank token skew

python tests/microbenchmarks/bench_moe.py \
  --world_size 4 \
  --model deepseek_v3 \
  --parallel_mode DEP \
  --backend TRTLLM \
  --balanced_total_num_tokens 896 \
  --per_rank_num_tokens 128 128 512 128 \
  --routing_dump_matrix \
  --output_file out/per_rank_skew.json

用途：研究某个 source rank token 明显更多时，max_num_tokens_per_rank、 padding、workspace 和 chunking 的变化。

案例 G：local-only baseline，估计最低通信量下界

python tests/microbenchmarks/bench_moe.py \
  --world_size 4 \
  --model deepseek_v3 \
  --parallel_mode DEP \
  --backend TRTLLM \
  --balanced_total_num_tokens 256 \
  --routing_mode forced \
  --comm_pattern local_only \
  --routing_dump_matrix \
  --output_file out/local_only_forced.json

用途：直接 supply top-k，让所有 selected slots 留在本 rank，用于估算“几乎没有跨 rank 通信”时的下界。它不是 native fused routing 路径，不能和 native 结果直接等价比较。

案例 H：routing pattern file 表达 CLI 表达不了的高级 routing 形状

# advanced_routing_pattern.json
{
  "ep_size": 4,
  "experts_per_rank": 4,
  "slot_dispatch_matrix": [
    [5, 0, 1, 2],
    [1, 5, 1, 1],
    [0, 2, 4, 2],
    [2, 1, 1, 4]
  ],
  "expert_histogram": [
    [5, 1, 1, 1],
    [0, 6, 1, 1],
    [0, 0, 7, 0],
    [2, 2, 1, 4]
  ]
}
python tests/microbenchmarks/bench_moe.py \
  --world_size 4 \
  --parallel_mode DEP \
  --num_experts 16 \
  --top_k 2 \
  --hidden_size 1024 \
  --intermediate_size 4096 \
  --quant FP8 \
  --routing_method RENORMALIZE \
  --backend CUTLASS \
  --balanced_total_num_tokens 16 \
  --routing_mode forced \
  --routing_pattern_file advanced_routing_pattern.json \
  --routing_dump_matrix \
  --output_file out/advanced_routing_pattern.json

用途：当每个 source rank 的目标 rank 分布都不同、且每个 target rank 内部 expert 热点也不同 时，CLI 的 receiver_hotspot、pair_hotspot、hotspot 只能表达少数规则化模式。 这类从 trace 或外部工具得到的任意矩阵需要用 --routing_pattern_file 同时固定 slot_dispatch_matrix 和 expert_histogram。

案例 I：从 JSON config 自定义搜索空间运行 dashboard sweep

{
  "model": "deepseek_v3",
  "workload": {
    "balanced_total_num_tokens": [64, 128, 256, 512],
    "routing_control": {
      "comm_pattern": "receiver_hotspot,hotness=0.75,rank=0",
      "expert_pattern": "balanced",
      "routing_dump_matrix": false,
      "seed": 42
    }
  },
  "search": {
    "backend": ["CUTLASS", "TRTLLM", "DEEPGEMM"],
    "parallel_mode": ["DEP", "TEP"],
    "comm_method": ["AUTO", "NVLINK_ONE_SIDED", "DEEPEP"]
  },
  "analysis": ["kernels"],
  "max_configs": 32,
  "output_file": "out/deepseek_v3_dashboard.json"
}
python tests/microbenchmarks/bench_moe.py \
  --config_file configs/deepseek_v3_dashboard.json

用途：面向 customer / custom benchmark 时，把“只关心的 backend、parallel layout、comm method” 固定在 config 里，避免 --backend ALL 或 --search full 生成过大的笛卡尔积。 当前 config 文件里的 search 只支持 backend、parallel_mode、 comm_method 三个 key；其它 runtime knob 请放在顶层或 workload/routing-control 字段里， 或通过 CLI 覆盖。注意：同样的子集声明，从 v2 起也可以直接写在 CLI 上，例如 --backend CUTLASS DEEPGEMM --comm_method NVLINK_ONE_SIDED DEEPEP， config file 主要用来固化方案、避免每次重复输入。

3. 重点：搜索空间怎么用

--search 决定脚本展开哪些 runtime 轴。搜索会先生成候选笛卡尔积，再用 backend capability、 parallel mapping、forced comm 合法性做剪枝。

--search 展开的轴 最常见用法
none 不展开，只跑当前 base config。 单个候选的 sanity 或复测。
backend 展开 backend 集合：未显式给 --backend 时默认全部 backend； 给 --backend ALL 等价；给 --backend CUTLASS DEEPGEMM 只搜这两个。 找哪个 backend 在给定 workload 下最快。
comm 展开 comm 集合：未显式给 --comm_method 时默认六种全部 (NVLINK_ONE_SIDED、NVLINK_TWO_SIDED、DEEPEP、 DEEPEPLOWLATENCY、ALLGATHER、AUTO)； 可用 --comm_method X Y 限定子集。 比较通信策略；通常配合 --parallel_mode DEP。
backend comm 同时展开 backend 和 comm，其它 runtime 轴使用当前 base config。 最常见的组合搜索；比 full 更可控。
parallel 展开 parallel 集合：未给 --parallel_mode 时默认 DEP、TEP、DTP、TTP； 可用 --parallel_mode DEP TEP 限定子集。CUSTOM 不能与其它模式组合。 比较 EP/TP 布局。
full 同时展开 backend、parallel、comm（按各自 --X / 默认全集规则），并比较 CUDA Graph on/off。 需要完整 runtime sweep 时使用，候选数会明显增加。
隐式开启搜索轴： --backend、--comm_method、--parallel_mode 传 >1 个值时 （或 --backend ALL），对应的搜索轴会自动加入 --search， 不必再手写。例如 --backend CUTLASS DEEPGEMM 单独使用，等价于 --search backend --backend CUTLASS DEEPGEMM。

组合 backend 和 comm 搜索空间

--search backend comm 只展开这两个轴，其它轴沿用 base config。 每个轴上跑哪些值，由各自的 --X 参数决定（未传则默认全集）：

  • --backend：未给 → 全部 backend；ALL 同义；给 list 则只搜 list。
  • --comm_method：未给 → 上述六种全部；给 list 则只搜 list。
python tests/microbenchmarks/bench_moe.py \
  --world_size 4 \
  --model deepseek_v3 \
  --parallel_mode DEP \
  --search backend comm \
  --balanced_total_num_tokens 128 256 \
  --max_configs 32 \
  --output_file out/backend_comm_search.json

上面命令省略了 --backend 和 --comm_method，两个轴都展开为全集。 若只想比较子集，例如 CUTLASS/DEEPGEMM 配 NVLINK_ONE_SIDED/DEEPEP： 

python tests/microbenchmarks/bench_moe.py \
  --world_size 4 \
  --model deepseek_v3 \
  --parallel_mode DEP \
  --backend CUTLASS DEEPGEMM \
  --comm_method NVLINK_ONE_SIDED DEEPEP \
  --balanced_total_num_tokens 128 256 \
  --output_file out/backend_comm_subset.json

这里没写 --search，因为多值的 --backend/--comm_method 会自动开启对应搜索轴。

重要： 推荐用空格分隔多个搜索轴，例如 --search backend comm parallel。 脚本也接受逗号写法 --search backend,comm,parallel，但空格写法和 --balanced_total_num_tokens、--analysis 这类已有多值 knob 更一致。

JSON config 里的自定义搜索空间

CLI 上 --backend X Y 已经能表达 backend/comm/parallel 子集；config file 的价值在于 把固定方案落盘、避免每次重复输入，以及把 workload 和搜索空间打包给客户复现。它的 search 字段只接受 backend、parallel_mode、 comm_method 三个 key；多值列表会自动开启对应搜索轴，单值则等价于把 --X 的默认值写在 config 里、不开搜索。 

{
  "model": "deepseek_v3",
  "workload": {
    "balanced_total_num_tokens": [128, 256]
  },
  "search": {
    "backend": ["CUTLASS", "TRTLLM"],
    "parallel_mode": ["DEP"],
    "comm_method": ["AUTO", "NVLINK_ONE_SIDED"]
  },
  "max_configs": 8,
  "output_file": "out/customer_dep_comm_compare.json"
}

上面的用例回答的是：“在客户指定的 DEP 部署形态里，CUTLASS/TRTLLM 搭配 AUTO 或 NVLink one-sided 哪个候选最好”。如果同一个字段同时出现在 CLI 和 config 中，CLI 显式参数优先生效。

按问题选择搜索空间

你想回答的问题 推荐命令组合
哪个 backend 最快？ --search backend（默认即全部 backend）
固定 backend 后哪个通信方式最快？ --backend TRTLLM --search comm
backend 和 comm 组合里谁最好？ --search backend comm --max_configs N
只想比较 backend 子集 (e.g. CUTLASS vs DEEPGEMM)？ --backend CUTLASS DEEPGEMM（多值会自动开启 backend 搜索）
只想比较 comm 子集 (e.g. NVLink one-sided vs DeepEP)？ --comm_method NVLINK_ONE_SIDED DEEPEP（多值会自动开启 comm 搜索）
是不是 parallel layout 影响更大？ --search parallel --backend TRTLLM（或 --parallel_mode DEP TEP）
客户只允许少量 backend/comm 候选，怎么避免全量笛卡尔积？ CLI 上 --backend X Y --comm_method A B 直接限定；要把方案落盘， 用 --config_file 在 search 里列出允许的 backend、parallel_mode、comm_method。

4. 控制 workload 和 routing 形状

Workload 分两层：token 数控制“有多少 token 进入 MoE”，routing control 控制“这些 token 的 selected experts 如何分布到 rank 和 local experts”。不传 routing-control 选项时，默认是 native + balanced_alltoall + balanced。

Token 数和 source-rank skew

参数 说明
--balanced_total_num_tokens 要 sweep 的全局总 token 数列表。每个值都会生成一个 workload，并尽量均分到各 rank。
--per_rank_num_tokens 显式指定每个 rank 的输入 token 数；长度必须等于 world_size，总和就是该 workload 的全局 token 数。和 --balanced_total_num_tokens 互斥。

Comm pattern：source → target traffic

名称 语义 示例
balanced_alltoall 每个 source rank 把 selected slots 尽量均匀发送到所有 target ranks。 --comm_pattern balanced_alltoall
receiver_hotspot 每个 source row 把指定比例的 slots 转向某个 target rank。 --comm_pattern receiver_hotspot,hotness=0.75,rank=0
pair_hotspot 只让一个 source→target pair 成为热点。 --comm_pattern pair_hotspot,hotness=0.5,src=0,dst=1
local_only 所有 selected slots 都留在本 rank，用于最低通信量 baseline。 --routing_mode forced --comm_pattern local_only
ring source i 全部发往 (i+1) % ep_size。 --routing_mode forced --comm_pattern ring

Expert pattern：target rank 内 local expert 分布

名称 语义 示例
balanced 每个 target rank 内 slots 在 local experts 间近似均匀。 --expert_pattern balanced
hotspot,hotness=... 每个 target rank 把指定比例的 slots 集中到一个 local expert。 --expert_pattern hotspot,hotness=0.5
hotspot,active_experts=... 每个 target rank 内只有指定数量的 local experts 承担全部 slots。 --expert_pattern hotspot,active_experts=2

Routing pattern file：同时固定 comm 和 expert 分布

如果需要从 trace 或外部工具精确复现 routing 形状，用 --routing_pattern_file。 这个文件同时提供 slot_dispatch_matrix 和 expert_histogram， 因此不要再把 file 输入拆到 --comm_pattern 和 --expert_pattern。 当每个 source row 都有不同的目标 rank 权重，或每个 target rank 需要不同的 local-expert 热点时， 这已经超过 CLI pattern 的表达能力，应该直接使用 routing pattern file。 

// routing_pattern.json
{
  "ep_size": 4,
  "experts_per_rank": 4,
  "slot_dispatch_matrix": [
    [64, 64, 64, 64],
    [64, 64, 64, 64],
    [64, 64, 64, 64],
    [64, 64, 64, 64]
  ],
  "expert_histogram": [
    [64, 64, 64, 64],
    [64, 64, 64, 64],
    [64, 64, 64, 64],
    [64, 64, 64, 64]
  ]
}

native 和 forced 怎么选

模式 适合场景 注意
--routing_mode native 想保留模型原生 logits / fused routing 行为，只是尽量把 routing 推向指定形状。 某些 routing method 不能精确表达请求形状，会出现 projected 或 rejected。
--routing_mode forced 想精确控制 top-k ids/scales，复现指定 dispatch matrix 或极端 workload。 会绕过 fused scoring；适合控制实验，不适合直接等价比较 native fused routing。

5. 如何看输出结果

rank0 会在 stdout 打印 header 和 result rows。传 --output_file 时，最终完整 payload 会写入 JSON 文件。 当前输出 schema version 是 5。 

{
  "schema_version": 5,
  "benchmark": "bench_moe",
  "environment": { "...": "..." },
  "model": { "...": "..." },
  "search": { "...": "..." },
  "base_config": { "...": "..." },
  "results": [],
  "rankings": []
}

先看 rankings

{
  "num_tokens": 256,
  "parallel_mode": "DEP",
  "best": {
    "backend": "TRTLLM",
    "requested_backend": "TRTLLM",
    "comm_method": "NVLinkOneSided",
    "cuda_graph": true,
    "use_low_precision_moe_combine": false,
    "score_us": 850.2,
    "status": "success"
  },
  "ranking": [...]
}

best 是同一个 num_tokens 和 parallel_mode 组内 score_us 最低的成功 case。skip/failed 候选仍在 ranking 中，方便看它为什么不可用。

再看 result row

字段 含义
workload本 case 的 token 设置、per-rank token 列表，以及 routing-control 请求。
requested_config用户请求或搜索展开得到的配置。
actual_config实际运行到的 backend、comm、scheduler、EP/TP、chunk 数。
statussuccess、skipped 或 failed。
skip_reason候选被剪枝、跳过或失败时的原因。
latency_us.score默认 score：每次迭代取最慢 rank，再对迭代求平均。
kernel_breakdownkernel 分类统计；--analysis none 时不会采集。
routing_control请求 routing 形状和实际观测形状的对比。

6. 常见问题和限制

现象 原因 / 处理方式
Custom shapes ... AUTO has no safe default 自定义 shape 必须显式指定 --routing_method。
forced comm 被 skip 非 DP、MoE TP、或 world_size=1 时部分通信方式没有意义，会被候选剪枝拒绝。
routing_realization.status="projected" routing method 不能精确反推请求的形状（最常见：DeepSeek-V3 grouped routing， Llama4 top1-only）。检查 max_abs_slot_error 判断偏差是否可接受。
routing_realization.status="rejected" 用户传了 --projection_policy reject 而又请求了不可精确表达的 pattern。 该 case 会作为 skipped 行输出，仍保留 routing_control summary。
forced 模式在 TEP 下结果不能和 native 比 forced 会 patch TRTLLMGenFusedMoE.run_moe，跳过 fused scoring； 它度量的是 supplied-topk 的执行路径，不是 native fused routing。
routing_pattern_file 报 row-sum 错 每行 row sum 必须等于 per_rank_num_tokens[src] × top_k； ep_size 必须和 runtime moe_ep_size 一致。
routing_pattern_file 和 comm/expert pattern 同时传 --routing_pattern_file 已经同时固定 dispatch matrix 和 expert histogram， 不能再组合非默认 --comm_pattern 或 --expert_pattern。
per_rank_num_tokens 报长度错 长度必须等于 world_size；它和 --balanced_total_num_tokens 互斥，总和就是该 workload 的全局 token 数。
phase_times_us 为空 当前 scheduler-side phase marker 尚未实现；只能看 latency 和 kernel breakdown。
某 backend 出现在 skipped 行 backend can_implement()、mapping 或 comm gate 不满足；看 skip_reason。
CUDA Graph timing 没有 kernel breakdown CUPTI 需要在 CUDA context 创建前初始化；失败时会标记 cupti_available=false 或跳过 breakdown。

7. 重点用户选项含义

启动方式

场景 命令形式 说明
单 rank --world_size 1 或不传 --world_size 脚本在当前进程内直接运行。
脚本自拉多 rank --world_size N 使用 mpi4py.futures.MPIPoolExecutor 生成 MPI worker。
外部 MPI mpirun -n N python tests/microbenchmarks/bench_moe.py ... 脚本检测到外部 MPI world size 后，直接在这些 rank 上运行。 
mpirun -n 4 python tests/microbenchmarks/bench_moe.py \
  --model deepseek_v3 \
  --parallel_mode DEP \
  --search backend \
  --balanced_total_num_tokens 128 512
Import 行为： 脚本会把 tests/unittest 加入 sys.path，以便直接复用 MoE unittest helper。 对 tensorrt_llm 主包，只有当当前源码树里存在已编译的 tensorrt_llm/bindings 时才优先使用源码树；否则会使用环境里已经安装好的 TensorRT-LLM wheel。这适合 OCI / 预构建容器里"源码 checkout + 已安装 wheel"的运行方式。

可以通过 --model 选择内置模型，也可以不传 --model，改用显式 shape 参数。 内置模型会提供默认 num_experts、top_k、hidden_size、 intermediate_size、默认 quant 和默认 routing method。

Routing control 选项

Routing control 让 benchmark 能 显式控制 dispatch / all-to-all 通信流量形状和 expert 热点， 用于复现可控的 routing workload。它和模型原生 routing 兼容：你可以让模型继续走原生 fused routing （native 模式），也可以直接 supply top-k ids/scales（forced 模式）。 完整设计见 BENCH_MOE_ROUTING_CONTROL_DESIGN.md。

核心参数

参数 默认值 说明
--routing_mode native native：保留模型原生 logits / fused routing，benchmark 反推 logits 把 top-k 推向计划的形状。
forced：直接 materialize topk_ids + 均匀 1/top_k scales， 绕过 fused scoring，但保留后续 metadata / permutation / grouped GEMM。
--projection_policy project 仅作用于 native 模式：
project：当原生 logits 无法精确表达时，使用最接近的合法 projection 继续运行， 并在结果里记录 routing_realization.status="projected" 与偏差。
reject：直接跳过该 case 并写入 skip_reason。
--comm_pattern balanced_alltoall source → target slot dispatch 形状。见下表。
--expert_pattern balanced 每个 target rank 内部的 local expert 直方图形状。见下表。
--routing_dump_matrix false 在每行结果中输出完整 observed_slot_dispatch_matrix / observed_token_dispatch_matrix / observed_expert_histogram。 默认只输出 summary，避免大 sweep JSON 膨胀。
--routing_seed 0 routing-plan materialize 时的确定性 seed。同 seed 输出一致。

Comm patterns

名称 语义 典型例
balanced_alltoall 每个 source rank 把 selected slots 尽量均匀发送到所有 target ranks。公平基线。 --comm_pattern balanced_alltoall
receiver_hotspot 每个 source row 把 hotness 比例的 slots 转向 rank=<k>。 研究接收端带宽 / 排队瓶颈。 --comm_pattern receiver_hotspot,hotness=0.75,rank=0
pair_hotspot 只让 src=<s> 行把 hotness 比例的 slots 转向 dst=<d>。研究单条 peer-link 热点。 --comm_pattern pair_hotspot,hotness=0.5,src=0,dst=1
local_only 所有 slot 都留在本 rank。研究最低通信量 baseline； 原生路由通常不能精确表达，需要 --projection_policy project 或显式 --routing_mode forced。 --comm_pattern local_only
ring source i 全部发往 (i+1) % ep_size。结构化 peer traffic。 --comm_pattern ring

Expert patterns

名称 语义 典型例
balanced 每个 target rank 内 slots 在 local experts 间近似均匀。 --expert_pattern balanced
hotspot,hotness=… 每个 target rank 把 hotness 比例的 slots 集中到 1 个 local expert。 --expert_pattern hotspot,hotness=0.5
hotspot,active_experts=… 每个 target rank 内只有 active_experts 个 expert 承担全部 slots。 --expert_pattern hotspot,active_experts=2

常用组合速查

没有 preset；下面是经常一起出现的 4 种组合，直接拼 --comm_pattern / --expert_pattern / --routing_mode / --projection_policy。

用途 显式 flag 组合
公平基线 --comm_pattern balanced_alltoall --expert_pattern balanced（即默认值）
Receiver hotspot 75% --comm_pattern receiver_hotspot,hotness=0.75,rank=0
Pair hotspot 50% --comm_pattern pair_hotspot,hotness=0.5,src=0,dst=1
Local-only 上限（不可精确表达就跳过） --projection_policy reject --comm_pattern local_only

各 routing method 的反推能力

Routing method capability 说明
Defaultexact_ids目标 expert ids 精确；scales 来自 softmax，不可任意指定。
Renormalize / RenormalizeNaiveexactids + scales 都可精确控制。
SigmoidRenormexact_idsids 精确；scales 受 sigmoid 限制。
Llama4top1_exact只能表达 top1；top_k > 1 时退化为 projected。
MiniMax2exact_with_zero_bias当 score-correction bias 为 0 时 ids 精确。
DeepSeekV3projected_or_exact受 n_group/topk_group 约束，可能 projected。
SparseMixerunsupportedv1 不支持精确反推，统一标 projected。

Backend、parallel、comm

--backend、--comm_method、--parallel_mode 都支持 nargs="+" 多值，默认分别是 TRTLLM、AUTO、DEP。 传 >1 个值会自动开启对应搜索轴（不必再写 --search）； --backend ALL 是"展开为全部 backend"的兼容写法，等价于在 --search backend 下不指定子集。脚本会先调用 backend can_implement() 做 capability gate， 不支持的候选会以 status="skipped" 写入结果。

通信方式

--comm_method 支持 AUTO、NVLINK_ONE_SIDED、 NVLINK_TWO_SIDED、DEEPEP、DEEPEPLOWLATENCY、 ALLGATHER，且支持 nargs="+" 多值（例如 --comm_method NVLINK_ONE_SIDED DEEPEP 同时搜索两种通信路径，会自动 开启 --search comm）。当前实现仍通过 TRTLLM_FORCE_COMM_METHOD 在单个 case 内注入强制通信方式，并在 case 结束后恢复环境变量。

说明： 当前所有候选在同一 worker 进程内顺序运行；大规模 sweep 需要注意跨 case 的进程内状态复用。

slot_dispatch_matrix 是 ep_size × ep_size 整数矩阵； 每行 row sum 必须等于 per_rank_num_tokens[src] × top_k。 expert_histogram 是 ep_size × experts_per_rank 整数矩阵； 每个 target-rank row sum 应该与 dispatch matrix 的对应 column sum 一致。
